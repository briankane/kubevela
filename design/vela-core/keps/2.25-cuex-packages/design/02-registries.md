# KEP-2.25 design 02: registries, resolution and loading

Phase 2 of the [KEP](../README.md): how a controller finds, fetches, checks and loads a package, and what a render records about it. It builds on [design 01](01-api.md) and reuses what KubeVela modules already do wherever it can.

## What exists today

| Kind | Lists versions | Reads a directory at a ref | Gives a pin | Code |
| --- | --- | --- | --- | --- |
| OCI | yes, semver tags | pulls a chart | manifest digest (HEAD) | `pkg/registry/component/oci.go`, `oci_revision.go` |
| Helm | yes, `index.yaml` | downloads a chart | the index has a digest; nothing reads it | `pkg/utils/helm`, `pkg/addon/backend_http.go` |
| GitHub | no | yes, contents API | no | `pkg/addon/reader_github.go` |
| Gitee | no | yes, contents API | no | `pkg/addon/reader_gitee.go` |
| GitLab | no | yes, tree and files API | no | `pkg/addon/reader_gitlab.go` |
| OSS | no | lists a bucket prefix | no | `pkg/registry/component/reader_oss.go` |

Modules already pull OCI charts by digest through `component.PullOCIChartFiles`, behind a `RevisionCache` (LRU, singleflight, a short failure TTL, stale content served when a probe fails) and a per-host rate-limit gate that honours `Retry-After`. Packages use the same path.

## A package is a Helm chart

Packed for Helm and OCI, a package is a chart, published the way modules are: one OCI repository per package, Helm's media types, `helm push` and `helm pull` work on it.

```
naming/
  Chart.yaml       # generated by build from cuex.yaml; never edited
  cuex.yaml
  *.cue
  module.wasm      # runtime wasm only
```

`Chart.yaml` carries `name` (the package's last path element), `version`, `type: library` so Helm refuses to install it, and annotations: `cue.oam.dev/path`, `cue.oam.dev/runtime`, `cue.oam.dev/abi`. `vet` refuses a `Chart.yaml` that disagrees with `cuex.yaml`, and `cuex.yaml` wins. Git and OSS hold the same directory, where `Chart.yaml` is optional.

A controller pulls the chart to read its metadata, which for a library is the whole package anyway; a WebAssembly module is a few hundred KiB with TinyGo.

## Resolving a version

Only the leader resolves; replicas load what `status.digest` names. In this phase a Package names an exact version or a digest, resolved once and on a change to its spec; ranges and re-resolving them arrive with [versions](04-versions.md), beside the check that makes following one safe.

| Kind | Versions from | `digest` is |
| --- | --- | --- |
| OCI | tags of `<url>/<package>` that parse as semver | the manifest digest |
| Helm | `index.yaml` entries for `<package>` | the index entry's `digest` (sha256 of the archive), checked on download |
| Git, Gitee, GitLab | `git ls-remote --tags` over HTTPS, tags `<package>/vX.Y.Z`, or `vX.Y.Z` for a package at the registry's root | the commit SHA the tag points at (peeled for annotated tags) |
| OSS | none | sha256 over the sorted file paths and contents; `vela cuex package digest <dir>` prints it |

- **One ls-remote for every Git host.** go-git's remote listing works against any HTTPS Git server with the registry's token, and returns tags with their SHAs in one request. The existing API readers then read the directory at that SHA, so a moving tag cannot change what was read.
- **Ranges follow semver.** Pre-releases match only a range that names one (`>=2.1.0-rc.1`), the highest match wins, and a version that disappears from the registry keeps serving with a `Resolved=False` condition rather than unloading.
- **Ranges, from phase 4, on each registry's `resolveInterval`, with jitter**, and on a change to the Package's spec. Resolutions against one registry share a concurrency cap and the rate-limit gate, which this extends from OCI to every kind.

## Fetching and checking

```
resolve ──► fetch at the pin ──► check ──► build ──► swap in
            (cache by digest)    cuex.yaml, CUE parses, deps,
                                 exports, ABI, limits
```

- **The cache is keyed by digest**, on disk, and is the same for every kind. A fetch writes a directory and renames it into place, so a crash never leaves half a package.
- **The check is `vet`'s**, run by the controller: `cuex.yaml` valid and agreeing with `Chart.yaml`, the CUE parses as one package named for the path, no `#provider`, every `#do` exported (WebAssembly), a supported ABI, within the namespace's limits, and the declared `dependencies` matching the CUE's imports. The leader runs it before moving `status.digest`, so a package that fails it never becomes the target: `Loaded=False` with the reason, and the previous digest keeps serving.

## Libraries kept in-cluster

A library's CUE is also written to a ConfigMap, so a replica restarting while the registry is down still loads it:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cuex-naming-v2-4f2c1a9e    # Package name and the digest's first 8 hex
  namespace: vela-system           # the Package's namespace
  labels: {cue.oam.dev/package: naming-v2}
  annotations: {cue.oam.dev/digest: "sha256:4f2c..."}
  ownerReferences: [{kind: Package, name: naming-v2}]
data:
  cuex.yaml: ...
  naming.cue: ...
```

The leader writes it before moving `status.digest`, and keeps the previous digest's ConfigMap until every replica reports the new one, so a replica that restarts mid-rollout finds what it needs either way. A replica reads the ConfigMap first and the registry only when it is missing. A library over 1 MiB gets `InCluster=False` and relies on the disk cache.

## Dependencies

- **Resolved as a definition's imports are**, in the dependent's namespace: `acme.com/types@v1` is vela-system's, `local/acme.com/types@v1` the dependent's own namespace's. One lookup, since the paths differ, and nothing is rewritten; a vela-system package cannot import `local/`.
- **Built once per Package**, against the instances of its dependencies, so the build-once sharing holds through the graph.
- **Swapped in as a set.** When `types` moves to 1.4, every dependent is rebuilt against it in the background, and the new `types` and the rebuilt dependents replace the old ones in one step. No render mixes a dependent built on 1.3 with `types` 1.4. A dependent whose range 1.4 falls outside (ranges arrive in phase 4) goes Ready `False`, reason `DependencyUnsatisfied`, and is swapped out in the same step.

## Recording what a render used

The compiler already selects the packages a template imports. It adds each one's path, version and digest to a collector in the context, beside the owner:

```go
// kubevela/pkg cue/cuex
func WithUsage(ctx context.Context) (context.Context, *Usage)
func (u *Usage) Packages() []PackageUse // path, version, digest; deduplicated
```

The Application controller starts one per reconcile, and writes the union into `ApplicationRevision.spec.cuexPackages` (design 01). What is recorded is what ran, including a range that resolved between two renders of one reconcile; two digests of one path in a revision mean exactly that, and `vela live-diff` shows both.

## Per replica

Only the leader writes status. Each replica reports through metrics and events:

| Metric | Labels |
| --- | --- |
| `cuex_package_loaded` (gauge, 1 when serving `status.digest`) | `namespace`, `package`, `digest` |
| `cuex_package_load_seconds`, `cuex_package_load_failures_total` | `namespace`, `package`, `reason` |
| `cuex_package_resolve_age_seconds` (leader) | `namespace`, `package` |

*Proposal.* The leader keeps an old digest's ConfigMap until every replica serves the new one, which it learns from a heartbeat each replica writes: `coordination.k8s.io` Leases named `cuex-loaded-<replica>`, listing the digests it serves. That also lets `vela cuex package show` say which replicas lag.
